一、需求背景

1.1 业务现状

当前主播任务体系主要解决“主播是否主动接触用户、是否完成任务、是否产生收礼”的问题，已经证明对主播活跃和用户承接有正向作用。

但现有体系仍偏短期：用户被分发给主播后，系统更关注本次任务是否完成，缺少对主播与用户之间关系是否持续、是否变深、是否正在流失的管理。

1.2 数据发现

关系延续偏低
14%~17%
T周期进入 top3 的关系，在 T+1 仍进入 top3 的比例较低。
深度关系贡献高
55%+
出现≥3个周期的深度关系，贡献 top3 关系金币的一半以上。
高价值用户多关系
2.88
P90+送礼用户平均关系数为2.88，不适合被单主播锁死。
核心判断：主播生态的关键问题不是“任务不够多”，而是任务没有围绕关系阶段组织。平台需要知道：哪些关系刚建立、哪些值得维护、哪些正在断裂、哪些需要召回。

三、需求范围

3.1 本期做什么

  1. 新增主播-用户关系标签：新关系、浅关系、连续关系、深度关系、预警关系、流失关系。
  2. 将主播任务拆成不同任务池：建立、深化、维护、预警、召回、探索。
  3. 优化主播端用户列表排序，让主播知道“该找谁、为什么找、做什么”。
  4. 新增用户端主关系保护与探索位策略，避免高价值用户被单点锁死。
  5. 新增运营后台配置和数据看板，支持灰度和效果追踪。

3.2 本期不做什么

  1. 不做永久绑定关系，不给主播用户“归属权”。
  2. 不替换现有主播等级 S/A/B/C，只新增软标签。
  3. 不在本期上线复杂模型，先使用可解释规则和可配置权重。
  4. 不承诺覆盖全量弱关系，本期优先围绕送礼 top3 主要关系。

四、产品方案概述

4.1 方案一句话

以主播-用户关系为核心对象，先判断关系阶段，再决定任务类型和分发策略，最后用关系结果评估任务价值。

4.2 主流程

1. 识别关系根据送礼、互动、任务生成关系标签。
2. 判断阶段区分新关系、深度关系、预警关系等。
3. 生成任务按关系阶段生成建立、维护、召回等任务。
4. 分发排序主播端与用户端分别按策略曝光。
5. 结果归因追踪是否留存、转深、复送礼。

4.3 关键产品原则

原则说明
关系优先于任务任务是推动关系的手段，不是最终目标。
维护优先于重建已形成深度关系的pair优先维护，因为金币贡献更高。
主关系不锁死保留主关系曝光，但给高价值用户探索位。
奖励看结果不只奖励完成动作，还要看后续关系是否延续或转深。

角色当前痛点本需求解决方式

消费用户当期可能只和一个主播互动，但跨周期容易断。保护主关系，同时通过探索位补充新关系，避免断裂后无人承接。

分发/算法缺少关系阶段和主播容量信息，分发意图不明确。提供用户关系状态、主播承接状态、任务优先级。

六、核心策略规则

6.1 关系阶段

关系阶段进入规则退出/流转规则任务策略
新关系该主播-用户pair首次发生有效触达，或首次进入送礼top3。有效触达包括：主播sayhi、双方≥3轮私聊、用户通过主播邀请进房停留≥5分钟、用户上麦停留≥3分钟。触发后72小时内无回复、无进房、无送礼，则降为普通候选关系；若T+1继续进入top3，进入连续关系。生成建立任务。任务有效期24小时；用户近24小时活跃才进入主播列表，高价值用户可放宽至72小时。
浅关系pair已产生过有效互动或1个周期进入top3，但active_periods<3且max_streak<2。下一周期继续进入top3，进入连续关系；若本周期top3消失，进入预警关系。生成深化任务。优先动作：5轮私聊、邀请进房、上麦、引导复送礼。
连续关系max_streak≥2，即同一pair连续2个3日周期进入top3。该阈值来自3月数据：max_streak≥2的消费侧pair贡献top3金币62.89%。连续关系任一周期未进入top3，进入预警关系；累计active_periods≥3后进入深度关系。生成维护任务。若用户近24小时活跃但pair无互动，优先展示给历史主播。
深度关系active_periods≥3，即同一pair在3月10个周期内至少3次进入top3。该阈值来自3月数据：供给侧深度pair贡献top3金币54.92%，消费侧贡献57.52%。1个周期未进入top3，进入预警关系；连续2个周期未进入top3，进入流失关系。生成维护/加深任务。主关系曝光优先，但不独占用户全部分发。
预警关系满足任一条件：上周期top1-top3关系本周期消失；或连续出现的pair金币较上周期下降≥50%；或高价值用户本周期top1对象发生切换。预警后72小时内重新进入top3或产生送礼，恢复到连续/深度关系；否则进入流失观察。生成预警任务。优先给历史主播；历史主播24小时未活跃、任务达上限或容量饱和时，才转给备选主播。
流失关系曾经是连续/深度关系，但连续2个3日周期未进入top3，且7日内无有效互动。用户近7日仍活跃，则进入召回池；召回成功后回到浅关系，不直接恢复深度关系。生成召回任务。任务有效期72小时，同一pair 3日内最多生成1次召回任务。

说明：本期所有“进入top3”均指主要送礼关系。若后续接入全量IM、进房、送礼边，可将弱关系纳入辅助判断，但不改变本期主规则。

6.2 用户关系状态

用户状态识别规则主播端任务配比用户端曝光策略
无稳定关系用户近30日无active_periods≥2的pair，且最近一个活跃周期关系数≤1。3月消费侧有87.56%的活跃送礼用户无深度关系，首段关系建立是最大池子。建立任务70%，深化任务20%，探索任务10%。优先分给探索型主播。新主播/候选主播曝光80%，历史弱关系20%。目标是建立第一段可延续关系。
单一强关系用户最近活跃周期top1占比≥80%，且深度关系数≤1。3月消费侧强排他周期占51.75%，但同一top1下期保留率仅25.74%。维护任务40%，探索任务30%，预警任务20%，深化任务10%。主关系70%，相似主播10%，新关系探索20%。不做单主播锁死。
多关系探索用户最近活跃周期关系数≥2，但无active_periods≥3的深度pair。深化任务50%，建立任务20%，维护任务20%，探索任务10%。历史互动主播50%，高匹配新主播30%，热门/在线主播20%。目标是把浅关系转深。
深度关系用户至少存在1个active_periods≥3的pair。若只有1段深度关系，仍保留探索位；若≥2段，进入多关系经营。维护任务50%，预警任务20%，深化任务20%，探索任务10%。主关系80%，相似主播10%，新关系探索10%。
高价值多关系用户最近一个3日周期送礼金额≥4,614金币（3月消费侧P90），且关系数≥3或深度关系数≥2。维护任务35%，深化任务30%，预警任务20%，探索任务15%。只分给经营型或高匹配主播。主关系60%，相似关系20%，新关系探索20%。目标是提升消费ARPPU。
预警/流失用户历史top关系消失、金额下降≥50%，或连续2个周期无主要关系但用户近7日仍活跃。预警/召回任务70%，维护任务20%，探索任务10%。历史主播70%，相似主播20%，新主播10%。

6.3 主播承接状态

主播标签判断规则适合承接限制规则
经营型主播满足任一：深度用户数≥2；或关系T+1留存率≥20%。3月主播侧deep_user_cnt≥2约占18.51%，属于较稀缺承接资源。深度关系、高价值多关系用户、预警/召回用户。若深度用户数≥4，判定为接近饱和，高价值新用户分配降权。
探索型主播平均新关系数≥2.2（主播侧P75），且平均任务数≥78（主播侧P75）。无稳定关系用户、新关系建立、多关系探索用户。若新关系T+1留存低于10%，只保留低价值探索任务，不分配高价值用户。
风险型主播周期收礼金额≥2,422金币（主播侧P75），且平均top1占比≥80%。保留原主关系维护，同时补新关系探索。用户列表中探索/建立任务不少于30%，避免收入单点依赖。
低效任务主播平均任务数≥78，但平均收礼低于552金币（主播侧P50），且深度用户数=0。普通建立任务和低风险探索任务。不进入高价值用户、预警用户、召回用户的优先承接池。

6.4 主播端每10个用户的任务池配比

主播标签建立深化维护预警/召回探索说明
经营型主播12322优先经营存量关系，保留少量探索。
探索型主播42112承担无稳定关系用户的关系建立。
风险型主播22213强制补关系池，降低top1依赖。
低效任务主播52102不给高价值预警/召回任务，先验证承接质量。

补位规则：若某任务池不足，优先用同用户价值层相邻关系阶段补位；仍不足时用普通建立任务补位。高价值用户不向低效任务主播补位。

七、功能需求详情

7.1 主播端用户列表

页面目标

让主播进入列表后能快速判断：这个用户为什么推荐给我、当前关系处于什么阶段、应该做什么动作、完成后有什么奖励和后续目标。

7.1.1 列表分组

主播端用户列表每次返回10个用户。列表不是简单按用户分层排序，而是先生成任务池，再按主播标签和任务配比混排。

分组进入条件展示优先级
今日必维护深度关系、连续关系，用户近24小时活跃，且当前主播近24小时未与其有效互动。P0
关系预警上周期top关系本周期消失、金额下降≥50%、高价值用户top1切换。P0
可加深关系浅关系或多关系探索用户，最近7日有互动或送礼。P1
新关系探索无稳定关系用户、单一强关系用户的探索位候选。P2
普通建立没有明显关系信号，但满足活跃、可触达、未达频控。P3

7.1.2 用户卡片展示内容

模块展示内容说明
用户基础信息头像、昵称、性别、在线状态、用户价值标签价值标签包括：低额、中额、高额、超高额。3月消费侧阈值：30/638/4,614金币。
关系标签新关系、浅关系、连续关系、深度关系、预警、流失召回仅主播/陪聊可见。最多展示2个标签：关系阶段 + 用户价值。
推荐原因如“上期给你送礼，本期未出现”“高价值用户，需要维护”“当前无稳定关系，可建立”让主播理解任务意图，避免机械刷任务。
推荐动作打招呼、私聊、邀请进房、上麦、维护、召回一个卡片只展示1个主按钮，避免动作过多。
奖励信息基础奖励、结果奖励、奖励等待状态结果奖励需说明触发条件，如“下周期继续送礼后发放”。
任务状态待完成、已完成、结果待归因、已失效、已达上限失效需展示原因，如“用户已被其他主播完成该任务”。

7.1.3 列表过滤规则

  1. 用户或主播处于封禁状态，不进入列表。
  2. 双方存在拉黑关系，不进入列表。
  3. 用户当日被sayhi达到上限，不展示sayhi建立任务，但可展示维护/召回任务。
  4. 主播该任务类型达到日上限，不展示该任务的奖励按钮，可展示无奖励的普通互动入口。
  5. 同一设备上同时存在主播账号和用户账号，该用户不参与奖励任务。
  6. 用户已经被其他主播完成唯一任务，该任务对当前主播展示为已失效。
  7. 高价值预警/召回用户不分配给低效任务主播。

7.1.4 刷新与频控

对象规则说明
列表刷新每次返回10个用户，手动刷新后重新按任务池配比取数。若任务池不足，按6.4补位规则补足。
用户曝光同一用户同一天最多出现在同一主播列表3次。避免主播反复看到同一低响应用户。
预警用户同一预警用户同一天最多被3个主播触达。历史主播优先，占至少1个触达位。
召回pair同一主播-用户pair 3日内最多生成1次召回任务。避免骚扰和刷召回。

7.2 关系任务

任务类型触发条件完成条件有效期/上限结果归因

已完成当前主播已完成动作。展示完成状态和奖励记录。
结果待归因动作完成，但等待后续关系结果。展示“关系延续后可获得追加奖励”。
已失效任务被其他主播完成、用户状态变化或过期。展示失效原因。
已达上限主播个人或全站奖励达到上限。不展示奖励按钮。

7.2.1 奖励发放原则

  1. 建立任务只发基础奖励，不直接发结果奖励。
  2. 深化、维护、预警、召回任务拆成“动作完成奖励”和“关系结果奖励”。
  3. 关系结果奖励不实时发放，需等待归因窗口结束。例如T+1继续进入top3、7日内复送礼。
  4. 若用户身上的唯一任务已被其他主播完成，其他主播不再获得该任务奖励。
  5. 如果全站奖励达到预算上限，任务仍可完成，但不再发奖励，前端必须明确展示。

7.3 主播中心任务页

主播中心需新增“关系任务”视角，让主播知道今日任务不是随机列表，而是围绕关系经营组织。

模块内容
今日任务概览建立、深化、维护、预警、召回、探索各类任务完成数。
今日重点用户展示高价值用户、预警用户、深度关系用户。
奖励进度基础奖励、结果奖励、待归因奖励分开展示。
任务说明解释不同关系标签含义，降低主播理解成本。

7.3.1 今日重点用户排序

排序用户类型原因
1高价值预警用户金额高且关系有断裂风险，优先挽回。
2深度关系用户已证明有关系价值，优先维护。
3浅关系高潜用户有机会转成连续/深度关系。
4无稳定关系但在线用户适合探索型主播快速建立关系。
5普通探索用户用于补足任务池。

7.4 用户端分发

用户端不需要直接展示“关系经营”概念，但推荐策略需要调整。

用户状态主关系/历史关系新关系探索说明
无稳定关系20%80%优先建立首段有效关系。
单一强关系70%-80%20%-30%不打断主关系，但保留探索位。
深度关系80%20%保护关系资产。
高价值多关系60%-70%30%-40%多主播组合承接，提高ARPPU空间。
预警/流失70%30%优先历史关系召回。

7.4.1 分发控制说明

  1. 上述比例只控制系统推荐曝光，不限制用户主动搜索、主动进房、主动私聊。
  2. 高价值用户的探索位必须使用高匹配主播，不进入随机池。
  3. 如果历史主关系主播离线超过24小时，主关系曝光可临时转给相似主播。
  4. 若用户连续2次对探索主播无响应，下一周期探索位从30%降到10%。

7.5 风控与边界规则

场景规则

刷进房进房停留需连续满足5分钟，中途离开重新计时。
刷上麦上麦停留需连续满足3分钟，静音不影响计时，但异常切换不计。
背包/活动礼物是否计入收礼任务需按现有礼物口径；默认只统计钻石礼物。
多主播同时触达唯一任务只给最先完成动作且满足风控的主播发放基础奖励。
用户关系状态变化任务生成后若用户进入深度关系，未完成的建立任务自动失效。

十、风险与待确认

问题风险建议
当前数据只含top3关系弱关系无法识别。本期先做主要关系，后续接入全量送礼、IM、进房边。
结果奖励可能被刷主播为奖励制造低质量互动。增加有效会话、进房时长、异常设备等风控。
探索位比例不确定探索过多可能打断主关系。通过AB实验验证 80/20、70/30 等配比。
主播容量阈值不准可能误伤优质主播。初期只做排序惩罚，不做硬过滤。
