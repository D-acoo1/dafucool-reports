一、需求背景

1.1 业务现状

当前主播任务体系主要解决“主播是否主动接触用户、是否完成任务、是否产生收礼”的问题，已经证明对主播活跃和用户承接有正向作用。

但现有体系仍偏短期：用户被分发给主播后，系统更关注本次任务是否完成，缺少对主播与用户之间关系是否持续、是否变深、是否正在流失的管理。

1.2 数据发现

关系延续偏低
14%~17%
T周期进入 top3 的关系，在 T+1 仍进入 top3 的比例较低。
深度关系贡献高
55%+
出现≥3个周期的深度关系，贡献 top3 关系金币的一半以上。
高价值用户多关系
2.88
P90+送礼用户平均关系数为2.88，不适合被单主播锁死。
核心判断：主播生态的关键问题不是“任务不够多”，而是任务没有围绕关系阶段组织。平台需要知道：哪些关系刚建立、哪些值得维护、哪些正在断裂、哪些需要优先挽回。

三、需求范围

本期定位：这不是一次性做完的“关系操作系统”，而是先把最小闭环跑起来：识别关系、给对任务、把人排对、看结果。本期优先复用现有主播任务和现有用户分层，不重新发明一整套复杂体系。

3.1 MVP（本期必须做）

模块本期方案为什么先做这个
关系状态只做 4 个状态：候选关系、新关系、稳定关系、预警关系。已经能覆盖“刚接触、接住了、值得维护、快断了”四个关键场景，足够支撑第一轮实验。
任务类型只做 3 类关系任务：建立、维护、挽回。主播最容易理解，服务端也可以直接复用现有 3轮/5轮私聊、单次收礼 100 钻等任务能力。
主播端列表每页固定 10 人，采用“2 个预警位 + 3 个稳定位 + 3 个新关系位 + 2 个补位”的轻量混排。历史关系贡献高，需要先保护；但也要保留新关系增长空间。
用户端分发只加 3 条规则：历史关系优先、预警关系优先回流、无稳定关系用户优先给新主播。先验证“关系优先分发”是否真的能提升付费率和消费 ARPPU。
结果看板先看 4 个指标：候选转新关系率、新关系 7 日转稳定率、稳定关系转预警率、预警 72 小时恢复率。先验证这套机制本身是否有效，不急着一次把所有经营指标都做全。

3.2 P1（MVP验证有效后追加）

方向内容上线前提
深度关系在稳定关系上继续细分出深度关系、多段深度关系。MVP 跑出明显的“新转稳”和“预警恢复”提升。
召回任务对已经断掉 7 日以上但用户仍活跃的关系，增加召回任务和用户侧召回。预警任务效果稳定后，再做更长链路召回。
主播软标签补充经营型/探索型/风险型等主播标签，用于更细的任务配比。现有 S/A/B/C 无法满足关系经营分流时再追加。
探索位精细化针对高价值多关系用户，分成主关系位、探索位、备选位。先证明高价值用户确实存在“主关系保护 + 新关系补充”的收益。

3.3 P2（长期建设）

方向内容
关系分数模型把送礼、私聊、进房、上麦、回访等信号做成统一关系分。
双端经营联动用户端、主播端、房间端统一用关系阶段做推荐与干预。
自动化预算分配基于任务效果，动态调节奖励系数和历史关系/探索关系配比。

3.4 本期明确不做什么

  1. 不做永久绑定关系，不给主播用户“归属权”。
  2. 不新增一整套全新的底层任务动作，优先复用现有私聊、收礼任务。
  3. 不在本期引入复杂模型和黑盒打分，全部规则可解释、可灰度、可回退。
  4. 不承诺识别全量弱关系，本期优先围绕“主要互动关系”和“主要送礼关系”。
  5. 不在本期做大规模后台配置页改造，先把核心策略跑通。

四、产品方案概述

4.1 方案一句话

以主播-用户关系为核心对象，先判断关系阶段，再决定任务类型和分发策略，最后用关系结果评估任务价值。

4.2 主流程

1. 识别关系根据送礼、互动、任务生成关系标签。
2. 判断阶段区分候选关系、新关系、稳定关系、预警关系。
3. 生成任务按关系阶段生成建立、维护、挽回任务。
4. 分发排序主播端与用户端分别按策略曝光。
5. 结果归因追踪是否转稳定、是否掉预警、是否恢复送礼。

4.3 关键产品原则

原则说明
关系优先于任务任务是推动关系的手段，不是最终目标。
维护优先于重建已形成稳定关系的 pair 优先维护，因为历史关系贡献更高。
主关系不锁死保留主关系曝光，但给高价值用户探索位。
小步快走本期先做最小闭环，优先复用现有任务和现有分层。

五、用户角色与使用场景

角色当前痛点本需求解决方式
主播/陪聊不知道今天该重点维护谁，只能按列表逐个打招呼。列表显示关系标签和推荐动作，告诉主播该做建立、维护还是挽回。
消费用户当期可能只和一个主播互动，但跨周期容易断。保护主关系，同时通过探索位补充新关系，避免断裂后无人承接。
运营只能看任务完成数和收礼结果，难判断关系是否沉淀。新增候选转新关系、稳定转预警、预警恢复等过程指标。
分发/算法缺少关系阶段信息，分发意图不明确。提供用户关系状态和历史主播优先规则。

六、核心策略规则

6.1 周期定义

名称定义用途为什么这样定
离线分析周期3 个自然日只用于本次 3 月 Excel 分析关系连续性。单日送礼波动太大，3 天能看连续性，又不至于拖得太长。
线上任务刷新周期1 个自然日任务释放、列表刷新、奖励上限、曝光频控。现有主播任务、曝光上限、奖励释放本来就是按自然日运转，复用成本最低。
新关系观察窗近 3 个自然日判断候选关系有没有被真正接住。和本次分析口径保持一致，且能更快回收实验结果。
稳定关系判断窗近 7 个自然日判断关系是否进入值得维护阶段。比单日稳定，又不需要为了固定分期额外开发一套复杂日历系统。
预警判断窗最近 3 日 vs 前 3 日判断关系是否明显降温。适合做快速提醒，不用等完整长周期过去才处理。
结论：Excel 里的“3 天周期”只是分析工具，不是线上系统周期。线上统一采用“自然日刷新 + 滚动窗口判断”，这样改动最小，也更符合现有任务体系。

6.2 关系状态机

候选关系只发生曝光或主播发起 sayhi，还没有用户响应。
新关系用户已产生第一次有效回应，说明关系被接住。
稳定关系近 7 日内重复发生有效互动或跨日送礼。
预警关系稳定关系开始降温，需要优先挽回。
普通池/P1召回MVP 不单独做流失召回，先退出任务池，后续版本补召回。
状态进入规则退出/流转规则本期处理方式
候选关系满足任一：1）该 pair 首次进入主播任务列表；2）主播对该用户发出 sayhi；3）系统首次给该 pair 下发建立任务。72 小时内若出现首次有效回应，则转为新关系；72 小时内无回应，则退出关系任务池，回到普通分发。只做“去私聊”引导，不单独发 sayhi 奖励。
新关系候选关系在 72 小时内出现首次有效回应。
有效回应口径：
①双方累计达到 3 轮私聊；
②用户当日累计送礼 ≥50 钻，记 1 个送礼日；
③普通用户通过主播邀请进房并与主播同房停留 ≥5 分钟。
说明：高价值用户不把进房作为有效回应主口径。		近 7 日内若再次发生有效回应，或形成第 2 个送礼日，则转为稳定关系；近 7 日内没有第二次有效回应，则回到普通分发池，不再继续给高优先级任务。进入建立任务池。
稳定关系近 7 个自然日内，同一 pair 满足任一：
①发生 2 次有效回应；
②发生 1 次有效回应 + 1 个送礼日；
③形成 2 个送礼日。
这样定义是为了线上尽量复用现有日级任务，不要求额外做固定 3 日分期。		最近 3 个自然日内无有效回应且无送礼日，则转预警关系；对高价值用户，如“最近 3 日金额 / 前 3 日金额”下降 ≥50%，也直接转预警。进入维护任务池。
预警关系稳定关系满足任一：
①最近 3 日无有效回应且无送礼日；
②高价值用户最近 3 日金额较前 3 日下降 ≥50%；
③历史主关系用户在最近 3 日内被其他主播替代为 top1 送礼对象。		72 小时内若完成 3 轮私聊或恢复单次送礼 ≥100 钻，则回到稳定关系；7 日内仍无有效回应，则退出 MVP 任务池，后续 P1 再接召回。进入挽回任务池，优先给历史主播。

补充口径：1）“送礼日”= pair 当日累计送礼金额 ≥50 钻；2）“高质量恢复”= pair 单次送礼金额 ≥100 钻；3）sayhi 本身不算有效回应，只有用户回复后才开始记入关系流转。

6.3 高价值用户定义

标签识别规则本期用途
普通用户不满足高价值或超高价值条件。正常进入建立/维护/挽回任务。
高价值用户满足任一：
①已有现有付费标签：新付费、近 3 日付费、30 日付费、大 R；
②最近 3 个自然日累计送礼 ≥638 金币。
638 金币取自 3 月消费侧活跃周期金额 P75。		候选保留时间从 24 小时放宽至 72 小时；建立任务升级为 5 轮私聊；优先给历史主播或现有 S/A 主播。
超高价值用户满足任一：
①大 R；
②最近 3 个自然日累计送礼 ≥4,614 金币。
4,614 金币取自 3 月消费侧活跃周期金额 P90。		不把进房类动作作为关系任务主动作；进入预警后前 12 小时只给历史主播看。

6.4 MVP 列表配比与补位规则

列表位每页数量进入规则补位逻辑
预警位2当前主播与用户处于预警关系，且用户近 72 小时仍活跃。不足 2 个时，优先由稳定位补足。
稳定位3当前主播与用户处于稳定关系，且近 24 小时双方无有效回应。不足 3 个时，由新关系位补足。
新关系位3候选关系或新关系用户，且用户近 24 小时活跃；高价值用户放宽到近 72 小时。不足 3 个时，由普通补位承担。
普通补位2沿用现有分层任务逻辑，从当前用户分层池补足。始终作为最后补位来源。

为什么采用 2/3/3/2：3 月数据里，出现 ≥3 个周期的深度关系贡献 top3 金币占比超过 55%，因此每页至少一半位置要保护历史关系；但同时关系 T+1 延续率只有 14%-17%，还必须保留足够的新关系位。

6.5 历史主播优先规则

场景本期规则
稳定关系历史主播优先拿到该用户；若历史主播离线超过 24 小时或当日任务上限已满，则按现有主播等级规则分给同档主播补位。
预警关系前 12 小时只给历史主播；12 小时后若历史主播未触达，开放 1 个同档备选主播；24 小时后仍未触达，则回到普通补位。
无历史关系用户直接按现有用户分层和主播分层发放，不额外增加复杂承接规则。

七、功能需求详情

页面目标

分组进入条件主按钮展示优先级

字段展示内容备注

7.1.3 列表内排序规则

分组排序规则

7.1.4 过滤与频控

  1. 用户或主播处于封禁状态，不进入列表。
  2. 双方存在拉黑关系，不进入列表。
  3. 同一设备上同时存在主播账号和用户账号，该用户不参与奖励任务。
  4. 同一用户在同一主播列表中，同一自然日最多曝光 2 次；预警关系不受第 2 次限制，但只允许历史主播优先看到。
  5. 候选关系 72 小时无回应自动失效；预警关系 7 日无恢复自动退出 MVP 任务池。
  6. 若用户身上的唯一奖励任务已被其他主播完成，当前主播仅保留普通互动入口，不再展示奖励按钮。

7.2.1 为什么本期不用“进房/上麦”做关系任务主链路

动作本期处理依据
sayhi只作为入口动作，不单独发奖励。单向 sayhi 很容易刷量，必须有用户回应才算关系被接住。
进房 5 分钟保留在原有普通任务中，但不进入高价值/预警关系任务主链路。你之前的关系分析里，进房任务对后续留存出现 -5.5pp 反效果；大 R 被进房完成率仅 0.1%。
上麦 3 分钟保留在通用任务，不进入本期 MVP 关系任务主链路。本期先集中做私聊和收礼两条最有效链路，避免前期任务面过宽。
单次收礼 100 钻保留为现有收礼任务，并作为维护/挽回结果的强信号。这是现有任务体系里最稳定的营收结果动作，历史奖励和埋点都已具备。

7.2.2 任务流转规则

当前状态发生事件流转结果
候选关系用户完成首次有效回应转为新关系，并下发建立任务。
新关系7 日内再次发生有效回应，或形成第 2 个送礼日转为稳定关系，并切到维护任务。
新关系7 日内无第二次有效回应退出关系任务池，回到普通分发。
稳定关系最近 3 日无有效回应且无送礼日转为预警关系，并下发挽回任务。
预警关系72 小时内完成 3 轮私聊或恢复单次送礼 100 钻恢复为稳定关系。
预警关系7 日无恢复退出 MVP 任务池；P1 再做召回。

7.2.3 奖励发放规则

  1. 建立、维护、挽回都只发“动作完成奖励”，本期不新增复杂的结果奖励结算。
  2. 挽回任务的私聊奖励采用 2 倍系数，即 3 轮私聊从 5 钻上浮到 10 钻，目的是让主播优先处理预警关系。
  3. 收礼 100 钻奖励继续沿用现有 25 钻，不单独新建一套关系奖励。
  4. 全站奖励预算、主播个人日上限、用户唯一任务归属，全部沿用现有主播任务风控规则。

十、风险与待确认

问题风险建议
当前数据只含top3关系弱关系无法识别。本期先做主要关系，后续接入全量送礼、IM、进房边。
近 3 日 / 近 7 日窗口是否足够稳窗口过短可能误报，窗口过长又会反应太慢。MVP 先用 3 日、7 日；上线后按预警恢复率和误报率再调窗长。
挽回任务可能被刷主播为拿 10 钻，制造低质量对话。私聊轮数要做文本去重和时间间隔风控；高频重复文本不算有效轮数。
高价值用户定义可能偏宽638 金币阈值若放得过宽，会让高价值池过大。先复用现有付费标签，再用 638 金币做行为兜底，灰度观察高价值池规模。
历史主播优先可能影响探索保护太多会压缩新关系增长。只在稳定关系和预警关系生效；无稳定关系用户仍以新主播曝光为主。
