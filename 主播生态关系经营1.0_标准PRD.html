一、需求背景

1.1 业务现状

当前主播任务体系主要解决“主播是否主动接触用户、是否完成任务、是否产生收礼”的问题，已经证明对主播活跃和用户承接有正向作用。

但现有体系仍偏短期：用户被分发给主播后，系统更关注本次任务是否完成，缺少对主播与用户之间关系是否持续、是否变深、是否正在流失的管理。

1.2 数据发现

关系延续偏低
14%~17%
T周期进入 top3 的关系，在 T+1 仍进入 top3 的比例较低。
深度关系贡献高
55%+
出现≥3个周期的深度关系，贡献 top3 关系金币的一半以上。
高价值用户多关系
2.88
P90+送礼用户平均关系数为2.88，不适合被单主播锁死。
核心判断：主播生态的关键问题不是“任务不够多”，而是任务没有围绕关系阶段组织。平台需要知道：哪些关系刚建立、哪些值得维护、哪些正在断裂、哪些需要召回。

三、需求范围

3.1 本期做什么

  1. 新增主播-用户关系标签：新关系、浅关系、连续关系、深度关系、预警关系、流失关系。
  2. 将主播任务拆成不同任务池：建立、深化、维护、预警、召回、探索。
  3. 优化主播端用户列表排序，让主播知道“该找谁、为什么找、做什么”。
  4. 新增用户端主关系保护与探索位策略，避免高价值用户被单点锁死。
  5. 新增运营后台配置和数据看板，支持灰度和效果追踪。

3.2 本期不做什么

  1. 不做永久绑定关系，不给主播用户“归属权”。
  2. 不替换现有主播等级 S/A/B/C，只新增软标签。
  3. 不在本期上线复杂模型，先使用可解释规则和可配置权重。
  4. 不承诺覆盖全量弱关系，本期优先围绕送礼 top3 主要关系。

四、产品方案概述

4.1 方案一句话

以主播-用户关系为核心对象，先判断关系阶段，再决定任务类型和分发策略，最后用关系结果评估任务价值。

4.2 主流程

1. 识别关系根据送礼、互动、任务生成关系标签。
2. 判断阶段区分新关系、深度关系、预警关系等。
3. 生成任务按关系阶段生成建立、维护、召回等任务。
4. 分发排序主播端与用户端分别按策略曝光。
5. 结果归因追踪是否留存、转深、复送礼。

4.3 关键产品原则

原则说明
关系优先于任务任务是推动关系的手段，不是最终目标。
维护优先于重建已形成深度关系的pair优先维护，因为金币贡献更高。
主关系不锁死保留主关系曝光，但给高价值用户探索位。
奖励看结果不只奖励完成动作，还要看后续关系是否延续或转深。

五、用户角色与使用场景

角色当前痛点本需求解决方式
主播/陪聊不知道今天该重点维护谁，只能按列表逐个打招呼。列表显示关系标签和推荐动作，告诉主播该做建立、维护还是召回。
消费用户当期可能只和一个主播互动，但跨周期容易断。保护主关系，同时通过探索位补充新关系，避免断裂后无人承接。
运营只能看任务完成数和收礼结果，难判断关系是否沉淀。新增关系留存、转深、断裂、召回看板。
分发/算法缺少关系阶段和主播容量信息，分发意图不明确。提供用户关系状态、主播承接状态、任务优先级。

六、核心策略规则

6.1 关系阶段

关系阶段判断规则系统动作
新关系主播-用户pair首次发生有效触达或首次进入top3。生成建立任务。
浅关系有互动或送礼，但未达到连续/深度关系。生成深化任务。
连续关系同一pair连续进入top3达到配置阈值，默认max_streak≥2。生成维护任务。
深度关系同一pair累计进入top3达到配置阈值，默认active_periods≥3。优先维护，允许加深任务。
预警关系上期top关系本期消失，或金额下降超过阈值。生成预警任务，优先给历史主播。
流失关系连续多个周期未进入top3且无有效互动。生成召回任务。

6.2 用户关系状态

用户状态识别规则分发策略
无稳定关系用户近N日无连续/深度关系。优先分给探索型主播，目标是建立首段关系。
单一强关系用户top1占比≥80%，且深度关系数≤1。70%-80%保主关系，20%-30%给探索位。
多关系探索用户关系数≥2，但还没有深度关系。分配给承接能力更强的主播，推动转深。
深度关系用户存在active_periods≥3的pair。优先维护主关系，监控断裂。
高价值多关系用户送礼金额P90+，关系数≥3。多主播组合承接，不做单主播锁定。
预警/流失用户历史top关系消失或连续无主要关系。优先历史主播召回。

6.3 主播承接状态

主播标签判断规则适合承接
经营型主播深度关系数高、关系留存高、收礼稳定。深度关系、高价值用户、预警召回。
探索型主播新关系数高、sayhi/私聊活跃、新关系留存高。无稳定关系用户、新关系建立。
风险型主播收礼高但top1占比过高，且top1保留低。保留核心关系，同时补探索任务。
低效任务主播任务很多但关系转深和收礼弱。降低高价值用户分配，优先普通探索任务。

七、功能需求详情

7.1 主播端用户列表

页面目标

让主播进入列表后能快速判断：这个用户为什么推荐给我，我应该做什么动作，完成后有什么奖励。

展示内容

模块展示内容说明
用户基础信息头像、昵称、性别、在线状态、用户价值标签沿用现有展示，新增价值标签。
关系标签新关系、深度关系、预警、召回等标签仅主播/陪聊可见。
推荐动作打招呼、私聊、邀请进房、维护、召回根据任务类型展示主按钮。
奖励信息基础奖励、可能的结果奖励结果奖励需说明“关系延续后发放”。
任务状态待完成、已完成、已失效、已达上限状态变化需要实时刷新或下次进入刷新。

交互规则

  1. 点击主按钮，执行当前推荐动作，如sayhi、私聊、邀请进房。
  2. 点击用户卡片，进入用户资料页，可查看该用户与当前主播的关系任务。
  3. 任务已失效时，不展示主按钮，展示失效原因。
  4. 主播达到日上限时，该任务类型不再展示可完成奖励。

7.2 关系任务

任务类型触发对象完成条件奖励建议
建立任务无稳定关系用户、新关系pairsayhi、≥3轮私聊、进房停留、上麦基础奖励
深化任务浅关系、多关系探索用户≥5轮私聊、邀请进房、产生送礼基础奖励 + 转深结果奖励
维护任务连续关系、深度关系私聊维护、进房互动、复送礼中等奖励，侧重关系不断裂
预警任务上期top关系消失或金额下降用户回复、进房、重新送礼触达奖励 + 恢复奖励
召回任务曾经深度关系但已流失用户重新互动或送礼较高结果奖励
探索任务单一强关系用户、风险型主播形成新有效互动基础奖励 + 新关系留存奖励

任务状态规则

状态定义展示方式
待完成当前主播可完成任务。展示主按钮和奖励。
已完成当前主播已完成动作。展示完成状态和奖励记录。
结果待归因动作完成，但等待后续关系结果。展示“关系延续后可获得追加奖励”。
已失效任务被其他主播完成、用户状态变化或过期。展示失效原因。
已达上限主播个人或全站奖励达到上限。不展示奖励按钮。

7.3 主播中心任务页

主播中心需新增“关系任务”视角，让主播知道今日任务不是随机列表，而是围绕关系经营组织。

模块内容
今日任务概览建立、深化、维护、预警、召回、探索各类任务完成数。
今日重点用户展示高价值用户、预警用户、深度关系用户。
奖励进度基础奖励、结果奖励、待归因奖励分开展示。
任务说明解释不同关系标签含义，降低主播理解成本。

7.4 用户端分发

用户端不需要直接展示“关系经营”概念，但推荐策略需要调整。

用户状态主关系/历史关系新关系探索说明

单一强关系70%-80%20%-30%不打断主关系，但保留探索位。
深度关系80%20%保护关系资产。
高价值多关系60%-70%30%-40%多主播组合承接，提高ARPPU空间。

十、验收标准

模块验收标准
关系标签同一pair可正确识别新关系、深度关系、预警关系、流失关系。
主播端列表不同用户展示对应关系标签、推荐动作和任务状态。
任务生成不同关系阶段生成不同任务，任务触发、失效、达上限逻辑正确。
分发策略单一强关系用户保留主关系曝光，同时出现探索位。
奖励基础奖励和结果奖励可拆分统计，达到上限后不再发放。
数据看板关系留存、转深、断裂、召回、任务有效关系率可按日查看。

十一、风险与待确认

问题风险建议
当前数据只含top3关系弱关系无法识别。本期先做主要关系，后续接入全量送礼、IM、进房边。
结果奖励可能被刷主播为奖励制造低质量互动。增加有效会话、进房时长、异常设备等风控。
探索位比例不确定探索过多可能打断主关系。通过AB实验验证 80/20、70/30 等配比。
主播容量阈值不准可能误伤优质主播。初期只做排序惩罚，不做硬过滤。
